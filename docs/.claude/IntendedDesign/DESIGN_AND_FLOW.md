# Design
### Framework (a "two-part combo" system):
- A C++ framework library acting as both an AP Client and IPC server, with additional Lua bindings
- A regular, minimal UE4SS Lua mod which utilizes the Lua C bindings to:
	- Load the framework config/profiles
	- Set up the IPC Server
	- Auto-discover any UE4SS mod "promises", which are contractual JSON files describing mod metadata (mod id, mod display name, mod description, enabled, mod capabilities for capability generation, list of other incompatible mod ids). If found (and enabled), this essentially "promises" two things: This mod will attempt to register to the framework (via our IPC protocol) as soon as it is ready and able to do so (3 minute timeout window by default), and this mod will fulfill the contractual obligations based on it's previously stated capabilities (such as what can be added to the AP randomization pool by this mod, or potential location checks this mod can provide, etc)
	- Waits for all registration promises to be fulfilled before allowing the AP client to connect to the AP server
- The C++ framework library logs *ALL* internal activity (including any warnings/errors) to a dedicated log file, but also looks specifically for registration from the Lua framework mod and pumps important messages to it so it can display those messages within the UE4SS console log and subsequently within UE4SS's dedicated log file (`ue4ss/UE4SS.log`) as a result 
### Mods:
- Can be either a UE4SS C++, or UE4SS Lua mod. In order to become "AP-enabled", they need to provide a JSON file within their own mod folders which contains metadata about their mod (mod id in the format of `author.game.mod`, semantic mod version, mod display name, mod description, supported range of target game versions, list of other mods this mod is incompatible with and/or optionally a range of unsupported versions of those mods, etc), following a schema which includes describing what their capabilities/intentions are
- Must be loaded by UE4SS *after* the framework has loaded (we can do so by having users modify their `ue4ss/mods/mods.json` and/or `ue4ss/mods/mods.txt` files, ensuring that the framework is loaded before any AP-enabled mods. Non-AP mods can still be loaded anytime before or after the framework, though)
- The framework should scan the local UE4SS ecosystem for these JSON "promises", and if enabled, add them to a queue to await for IPC registration from all enabled AP mods
- In order for a mod to register and send/receive IPC messages to/from the framework, we should provide a minimal C/C++ library with Lua C bindings (and Lua wrapper, for UE4SS Lua mods) for these mods to utilize within their own normal UE4SS environments. This library will act as an IPC client, with JSON support, logging support and various other helper functions. Note that in order to also support UE4SS C++ mods, we provide a static `*.lib` file and headers to include, so that UE4SS C++ mods can link against the library and call methods directly. The only concern for UE4SS C++ mods is that UE4SS typically loads them before any UE4SS mods, which means that they would have to delay registration with the framework and figure out when the best time to register would be (possibly using UE4SS-based reflection to know if or when the framework is loaded into the UE4SS ecosystem, or simply just periodically attempting registration until they finally receive a response message from the framework)

### AP Server (our `palworld.apworld` Python implementation):
- Looks at a provided `APCapabilities.json` file generated by the framework, populates the AP ecosystem with items, locations etc based upon the entire list of what is possible
# Intended Flow
1.) Run Palworld -> UE4SS loads our framework, discovers mod capabilities ("promises"), generates `APCapabilities.json` once all mods register to the framework
2.) Open Archipelago -> Install our `palworld.apworld` (if not already installed) -> click Generate (this should take in our generated `APCapabilities.json` so the apworld knows what can be randomized, generates a multiworld `AP_*.zip` file) -> click Host (and select our generated `AP_*.zip` multiworld)
3.) Restart Palworld -> Framework waits for all discovered mods to register again -> framework connects to AP server -> main loop begins
4a.) AP server receives item from some other game -> AP server sends item to framework -> framework sees item, knows which mod to send it to -> mod enforces it's earlier "promise" by enforcing it's capability rule (ie, forcing a specific tech to be unlocked, etc)
4b.) Mod finds location check issued by server -> mod sends notification to framework -> framework notifies server -> server notifies other game about sent item

# Why?
- Allow me to explain based upon this discord conversation:
```
I'll give you a couple of example scenarios:
- Chest shuffling might be possible offline (AP side) if we preemptively knew the locations of all overworld chests. But would require runtime support (Lua/C++ mod side) to dynamically know when which chest was opened, and force some other item to be obtained instead of the original item (depending on what the AP server says to do).
- Region locking would be possible offline (AP) if we have a list of known regions and we want to enforce some kind of linear or branching logic which states where a player is allowed to go before being able to go elsewhere. But would require a runtime mechanism (mod side) to create and destroy invisible walls or whatever based on AP checks.
- These are just hypothetical examples, not actual real-world scenarios.

If we keep an extensible system, we can just allow the community to create whatever AP/mod functionality they want to see, instead of us being the ones to predetermine everything.
We can offer some basic, default mods for people to use, and allow for those to be disabled or removed or replaced with some other set of features.

The main design philosophy here is that *mods are responsible* for telling the system what they are capable of, since without a mod there would never be anything to randomize in the first place. It's not entirely 100% static generation, because Palworld requires a lot of specialized runtime mod operations. So we made it extensible instead, where mods literally determine what is possible from the start, and on good faith they fulfill their contractual promises to the system.
```
	- Essentially, we have this design to solve the Palworld-specific issue of having a single, large, monolithic, "all-in-one" pre-defined mod, which is prone to stability issues and crashes. Instead, we leave it open to the modding community via providing an open, extensible framework which any size mod or set of mods can work collaboratively to create different experiences in Archipelago, and hopefully without disturbing or drastically modifying a normal UE4SS ecosystem
